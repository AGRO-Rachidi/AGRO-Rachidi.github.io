A department-isolated file server, from Unix groups to Samba

Four departments, eleven employees, one rule: each team sees only its own files. Built with groups, SGID and POSIX ACLs, automated with an idempotent Bash script, shared over the network with Samba, and tested from a real SMB client.

Context

Second project of the systems part of my internship at FusionSoft Labs: a file server for « TechCorp », a fictional company with HR, IT, Finance and Management, eleven employees in total, built in an isolated container lab.

Problem

Each department must reach its own documents and a common space, and nothing else. The setup also had to be reproducible: typing the same seven commands per department by hand had already produced real mistakes.

Objective

Least privilege on disk, the same guarantees over the network, and a setup script that can be run again safely.

Architecture

  • One Unix group and one folder per department, mode 770 with the SGID bit, plus a common folder reached through a shared secondary group.
  • POSIX ACLs on the parent folder grant each department the traverse right (x) only.
  • An idempotent Bash script with three functions (create service, create users, set up folders) that checks the current state before acting.
  • Samba shares under /srv (per the Filesystem Hierarchy Standard), one per group: valid users = @group, create mask 0660, configuration validated with testparm.

What I did

  • Built the model by hand first, then replaced the repetition with a script. Employee entries are stored as user:group and split with Bash parameter expansion, without calling external commands.
  • Fixed real scripting bugs along the way: a test that executed a variable instead of evaluating it; useradd failing silently while the script printed « created » (fixed by checking the exit code); comparing a name against the whole getent line instead of its first field.
  • Opened the setup to the network with Samba: a system account and a separate Samba account per employee, created in a loop.
  • Tested everything with each employee's real account, never as root.

Difficulties and how I solved them

  • A correctly configured user was still denied access to their own folder. The cause was the parent folder: reaching a file requires the traverse right on every directory of the path. A folder has only one owning group, and « chmod o+x » would have opened traversal to every account on the system, which breaks least privilege. POSIX ACLs (setfacl -m g:<group>:x) solved it without changing the owner.
  • SGID guarantees the group of a new file, not that the group can write to it. With the default umask 0022, new files were -rw-r--r--. A working team folder needs both settings, and umask persistence needs a profile file or default ACLs.

Results

  • A file server where every allowed access works and every forbidden access fails exactly where it should, locally and over SMB.
  • A reusable, idempotent provisioning script, and a written explanation of each permission choice.

Known limits

  • A lab in a container with fictional accounts, not a company directory.
  • Identities are local; there is no central directory (LDAP or Active Directory).
  • In the repository, the Samba part is a compilation of commands that were run and validated one by one, not an original script. The README says so.

What I would improve

  • Default ACLs so group write no longer depends on each user's umask
  • Central identities with Samba AD or LDAP
  • Audit logging of share access
