Securing a Linux server in seven days

Took over a simulated accounting server with production requirements: key-only SSH, default-deny firewall, encrypted backups proven by a real restore, self-healing web service, and an incident investigation.

Context

Mission « Excellence Cyber », run during the systems-administration part of my internship at FusionSoft Labs. I played a junior sysadmin taking over the server of a fictional company's accounting department, with a written specification: recovery point objective (RPO) of 24 hours and recovery time objective (RTO) of 30 minutes.

Problem

A freshly installed server with no protection. Every requirement (access, data separation, backups, availability, traceability) had to be met and demonstrated, not just configured.

Objective

Bring the server to the specification in seven days, prove each control with a test, and close the week with an honest self-audit.

Architecture

  • One Ubuntu 24.04 server in a Docker container, on its own isolated Docker network with a fixed address.
  • Three named accounts: two administrators with sudo, one service account with no interactive shell. Each has its own ed25519 key pair protected by a passphrase.
  • SSH on a non-default port, root login and password authentication disabled; UFW denies all incoming traffic except SSH from the administration subnet.
  • A nightly job compresses the accounting data, encrypts it with GPG (AES-256), deletes the clear archive and keeps seven days of history.
  • Nginx supervised by supervisord; connection history available through last and lastlog.

What I did

  • Day 1: isolated network, named accounts, key-only SSH and firewall. Public keys were copied in with docker cp, because password authentication was never enabled, not even temporarily.
  • Days 2–3: dedicated accounting folder with the SGID bit; encrypted backup script with seven-day rotation, then a full restore test.
  • Days 4–5: automatic restart of the web service, and connection traceability.
  • Day 6: an unannounced incident (a customer claims to have received an invoice they never ordered), investigated without knowing the answer.
  • Day 7: self-audit of every requirement and a mission report.

Difficulties and how I solved them

  • UFW would not start: a standard container lacks the kernel capabilities it needs. I froze the work with docker commit and recreated the container with NET_ADMIN and NET_RAW, without losing anything.
  • No systemd or journald inside the container, so the usual tools for automatic restart and logs were missing. I used supervisord for the service and last/lastlog for connection history, which work without systemd.

Results

  • All seven controls of the final audit met: SSH root blocked, key-only authentication, default-deny firewall, encryption at rest with seven-day rotation, restore tested and timed, automatic restart, consultable connection history.
  • A lesson I kept: finding nothing abnormal in an investigation is a result. It points to another explanation.

Known limits

  • A simulated server in a container, not a production machine with real users.
  • The backup passphrase is stored on the server itself. In production it should live in an external secrets manager.
  • The scripts in the repository were rebuilt after the container was deleted. They reproduce the commands documented in the original report, and the repository says so.

What I would improve

  • Move the backup secret to a dedicated secrets manager
  • Forward logs to a central collector or SIEM instead of reading them on the host
  • Automate the final audit as a repeatable compliance check
