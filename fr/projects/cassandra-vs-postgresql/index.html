Cassandra en pratique : un cluster de 3 nœuds, un test de panne et dix ans de données

Avec deux camarades, j'ai exploré la façon dont Cassandra gère de gros volumes de données : nous avons conçu le schéma à partir de nos requêtes, fait tourner un cluster de 3 nœuds qui répondait encore avec un nœud arrêté, et comparé Cassandra à PostgreSQL sur dix ans de mesures de capteurs simulées.

Période
Octobre – novembre 2026
Statut
Terminé · projet de groupe (3 étudiants)
Type
Projet académique
  • Apache Cassandra 5.0
  • CQL
  • PostgreSQL 15
  • Docker
  • Python
  • nodetool
  • LaTeX
Dépôt : rapport, CQL, banc de mesure, résultats bruts

Contexte

Groupe 4 du cours de systèmes d'information (ENSGMM, 2026–2027), trois étudiants, sous la supervision de l'enseignant. Le sujet : comment les bases orientées colonnes gèrent des volumes massifs de données distribuées, et ce qu'elles sacrifient en échange.

Problème

Un réseau de capteurs écrit une mesure toutes les quelques secondes, pendant des années. La base doit garder des lectures rapides quand l'historique grossit, survivre à la perte d'une machine et tenir dans le budget disque.

Objectif

Montrer la logique du modèle sur un vrai cluster, puis mesurer où il gagne et où il perd face à une base relationnelle bien indexée.

Architecture

  • Schéma conçu à partir de six requêtes, d'où quatre tables. La duplication est normale dans ce modèle.
  • Clé de partition (sensor_id, day) : le découpage par jour borne chaque partition à environ 8 640 lignes par capteur et par jour. Une clé de clustering sur l'horodatage rend les plages temporelles rapides.
  • Trois nœuds Cassandra 5.0 sous Docker avec un tas Java limité ; keyspace en RF = 3, plus un keyspace de test en RF = 1 pour rendre le partitionnement visible.
  • Un banc de mesure en Python charge une année à la fois (1,75 million de lignes chacune) dans Cassandra et PostgreSQL, puis chronomètre les mêmes requêtes.

Ce que nous avons fait

  • Explication du modèle dans le rapport : modèle de données Bigtable, partitionnement Murmur3, réplication, cohérence ajustable, chemins d'écriture et de lecture, comparaison avec HBase et le relationnel.
  • Construction du cluster et de l'étude de cas IoT, avec conservation des sorties réelles de cqlsh et nodetool comme preuves.
  • Banc de mesure sur dix ans et migration PostgreSQL → Cassandra avec scripts de vérification.
  • Rédaction du rapport et de la présentation en LaTeX.

Ce qui a coincé, et comment je l’ai résolu

  • Avec RF = 3 sur trois nœuds, chaque nœud détient 100 % des données : la réplication était visible, pas le partitionnement. Un second keyspace en RF = 1 et nodetool getendpoints ont montré quel nœud possède quel capteur.
  • Un seul ordinateur ne peut pas absorber le débit de l'énoncé. Nous avons ramené l'intervalle de mesure de 10 secondes à 15 minutes, et nous l'avons écrit en expliquant l'effet sur les résultats.

Résultats

  • Une image claire du compromis : Cassandra garde les requêtes prévues rapides quelle que soit la profondeur de l'historique, écrit et stocke efficacement, mais exige que chaque question soit décidée avant la première écriture.
  • Leçon de conception : dans une base orientée colonnes, modéliser, c'est concevoir les chemins d'accès autant que les données.

Ce que ça ne fait pas (encore)

  • Tous les nœuds sur une seule machine : rien n'est mesuré sur l'ajout de machines, le principal atout de Cassandra.
  • Les temps incluent les pilotes Python et le réseau Docker.
  • Travail de groupe : le rapport et le code appartiennent aux trois auteurs.

Ce que j’améliorerais

  • Refaire le banc de mesure sur plusieurs machines
  • Mesurer au débit d'origine (10 s) sur une fenêtre de temps plus courte
